## Cross-check between the two reviews

The two reviews were produced independently. Where they overlap and where they diverge:

**Agreed, both verified independently**

- `quantize_aef` turning nodata into a valid `0` (A1 here, §4.1 there).
- The int8 merge mask being unsatisfiable, breaking multi-zone TESSERA (A2 / §4.2). Astra's
  version is stronger — see below.
- `ModelPixelScale` y-sign (A3 / §4.4); Astra adds that the tiepoint's raster indices `I, J` are
  ignored too, so the correct form is `Affine(sx, 0, X - I*sx, 0, -sy, Y + J*sy)`.
- CRS grouping under `"unknown"` (A4 / §4.5), bare-CRS → 4326 (A7 / §4.5),
  `limit=0` (A8 / §4.15), vars unique to later zones (A9 / §4.3),
  antimeridian (A13 / §4.8), `async` query and the Jupyter failure (B1 / §1.1),
  `/tmp` default (B3 / §1.3), no dataset abstraction (D1 / §2.1), no host abstraction (D2 / §2.2),
  extraction and chip APIs as the next features (D3, D4 / §2.3, §2.4), keep obstore (C7 / §3.11),
  S3 Express / CRT / Mountpoint not worth it (C9 / §3.12), GPU decode not worth it (C11 / §3.14).

**Astra overturned one of my findings — it is right**

- **B5 was wrong: `rasterio` is a genuine hard dependency.** I claimed it could be dropped because
  nothing in the package imports it. Astra pointed out it is needed by the ODC reprojection path.
  **Verified**: `odc/geo/warp.py` does a module-level `import rasterio.warp`, and `odc-geo` does
  not declare rasterio itself — so `xr_reproject`, and therefore `reproject_datatree`, fails at
  import without it. Declaring it in `pyproject.toml` is correct. B5 below is struck through.

**Astra refined two others**

- **C4 (range coalescing)**: coalescing adjacent ranges and HTTP multipart-range requests are
  different mechanisms, and **S3 does not serve multiple disjoint ranges in one GET**. So the win
  is merging *adjacent* ranges under a read-amplification budget, not batching disjoint ones.
  Astra also checked VirtualiZarr 2.7.3 and found it fetches ranges individually with
  `get_partial_values` unimplemented — so this is upstream work, and its estimate (0–30%
  end-to-end, layout-dependent) is better calibrated than mine.
- **A2** is worse than I described. Astra verified the merge picks each *variable* independently,
  so raw TESSERA can take `embeddings` from one zone and `scales` from another: a first zone with
  code `0`/scale `NaN` followed by a valid zone with code `10`/scale `2` yielded
  **code 0, scale 2, value 0 instead of 20**. The fix must be one shared validity mask across
  `embeddings`, `scales` and the quality variables — not just stamping a nodata attr.

**Astra found these; I missed them. All verified by it, and worth treating as first-class.**

## A. Correctness

### A1 (P0) `quantize_aef` silently turns nodata into a valid zero embedding

[utils.py:167-173](../aef_loader/utils.py#L167-L173). `dequantize_aef` maps `-128 → NaN`, and
`quantize_aef` is documented as its inverse. But NaN survives `np.sign`, `np.sqrt`, `np.round`
and `np.clip` unchanged, and `.astype(np.int8)` of NaN is undefined behaviour.

**Verified** (numpy 2.5.3, Windows x64): `quantize_aef(np.array([np.nan], dtype=np.float32))`
returns **`0`**, with `RuntimeWarning: invalid value encountered in cast`. `0` is a legitimate
embedding code that dequantizes back to `0.0` — so a `dequantize → quantize` round trip converts
every nodata pixel into real data, with no error and no way to detect it downstream.

Fix: mask before the cast.

```python
quantized = np.round(sign * magnitude * divisor)
quantized = np.clip(quantized, -127, 127)
quantized = np.where(np.isnan(quantized), AEF_NODATA_VALUE, quantized).astype(np.int8)
```

### A2 (P0) Multi-zone mosaics silently discard every zone after the first, for int8 data with no nodata attr

[utils.py:429-438](../aef_loader/utils.py#L429-L438). The merge picks its mask like this:

```python
nodata = combined[var].attrs.get("nodata", combined[var].attrs.get("_FillValue"))
if nodata is not None and not (isinstance(nodata, float) and math.isnan(nodata)):
    mask = combined[var] == nodata
else:
    mask = combined[var].isnull()
```

**Verified**: `isnull()` on an integer dtype is always `False`. So when the attrs are absent,
`xr.where(all_False, ds, combined)` returns `combined` everywhere and zones 2..n contribute
nothing at all.

AEF is safe — [reader.py:704](../aef_loader/reader.py#L704) stamps the attrs via
`set_aef_nodata`. **TESSERA is not**: [tessera.py](../aef_loader/tessera.py) never stamps them,
and raw int8 `embeddings` therefore reaches `reproject_datatree` with no nodata attr. Any TESSERA
AOI spanning two UTM zones silently mosaics to zone 1 only — and that is not an edge case: the
README's own example bbox starts at 5.6°E, 0.4° from the zone 31/32 boundary at 6°E.

Fix, both halves:
- `reproject_datatree`: raise if a variable has an integer dtype and no usable nodata attr,
  rather than falling through to a mask that cannot ever be true.
- `tessera.py`: stamp nodata on its outputs (and see D1 — this is a symptom of AEF constants
  being unavailable to the TESSERA path).

### A3 (P1) `ModelPixelScale` affine has the wrong y sign

[reader.py:99](../aef_loader/reader.py#L99), with the original author's own `TODO` on the line
above. `Affine(sx, 0, x, 0, sy, y)` uses a **positive** `sy`. GeoTIFF's `ModelPixelScale` is
`(|sx|, |sy|, |sz|)`; a north-up image needs `e = -sy`.

**Verified**: with `Affine(10, 0, 500000, 0, 10, 4000000)`, row 0 maps to y=4000005 and row 10 to
y=4000105 — y increases as you go *down* the raster, i.e. the image is flipped.

`_get_geobox_from_dataset` **prefers** this path whenever `model_pixel_scale` is present
([reader.py:147](../aef_loader/reader.py#L147)), so a COG carrying both tags gets the flipped
geobox even though the correct `ModelTransformation` is right there. AEF tiles carry only
`ModelTransformation`, so AEF output is unaffected today — but this is the fallback path for
every dataset added from here on (see D1/D2), so it is a landmine rather than a dead branch.

### A4 (P1) Tiles with no UTM zone are mosaicked across different CRSs

[reader.py:488](../aef_loader/reader.py#L488) buckets every tile with `utm_zone=None` under the
single key `"unknown"`. [reader.py:516](../aef_loader/reader.py#L516) then takes
`zone_tiles[0].crs_epsg` as *the* CRS for that whole bucket, and `combine_by_coords` merges its
members by coordinate value. Tiles from genuinely different CRSs get overlaid as though they
shared one grid — numerically plausible output, geospatially meaningless, no warning.
`_combine_tiles_single_zone`'s docstring states "All tiles must be in the same CRS" but nothing
enforces it.

Fix: group by `(utm_zone, crs_epsg)`, or assert a single distinct `crs_epsg` per group.

### A5 (P1) Extra data variables are silently dropped

[reader.py:697-705](../aef_loader/reader.py#L697-L705): `data_var = list(combined.data_vars)[0]`,
then `combined = da.to_dataset()` — everything except the arbitrarily-first variable is
discarded. Correct for single-array AEF COGs; silent data loss for any COG that virtualizes to
more than one array.

### A6 (P1) Index cache write is not atomic and a truncated file is cached forever

[index.py:157](../aef_loader/index.py#L157) does `local_path.write_bytes(data)` for a **78 MB**
download. A Ctrl-C or crash mid-write leaves a truncated parquet, and
[index.py:121](../aef_loader/index.py#L121) (`if local_path.exists() and not force`) then treats
it as a valid cache on every subsequent run. `load()` fails with a raw pyarrow error that never
mentions `download(force=True)`.

[cache.py:480-482](../aef_loader/cache.py#L480-L482) already gets this right (temp file +
`replace()`). Apply the same pattern here.

### A7 (P2) Unrecognised CRS strings silently become EPSG:4326

[index.py:307](../aef_loader/index.py#L307):
`crs_epsg=int(crs.split(":", 1)[1]) if ":" in crs else 4326`. A bare `"32633"` yields **4326** —
a wrong CRS rather than an error, which then propagates into every geobox built from that tile.
Parse properly and raise on failure.

### A8 (P2) `limit=0` returns every tile

[index.py:276](../aef_loader/index.py#L276): `if limit:` — `0` is falsy, so `limit=0` means
"no limit". Use `if limit is not None`.

### A9 (P2) Variables unique to later zones are dropped on merge

[utils.py:419-421](../aef_loader/utils.py#L419-L421) iterates `combined.data_vars` — zone 1's
variables only — and `continue`s on anything missing. A variable present in zone 2 but not zone 1
never reaches the output. (Also: assigning into `combined` while iterating `combined.data_vars`
is safe only because the keys never change; snapshot with `list(...)`.)

### A10 (P2) A bbox that misses a tile produces a degenerate zero-size array

[reader.py:635-636](../aef_loader/reader.py#L635-L636) crops each tile with label-based
`ds.sel(...)`. A tile that does not overlap `bbox` yields a 0×0 spatial array, which is then
`expand_dims`'d and fed to `combine_by_coords` rather than being skipped. This becomes more
likely if you adopt C1's bbox-overlap prefilter, which admits a few non-overlapping tiles by
design. Filter out empty crops after `_crop_to_bbox`.

### A11 (P2) Reader teardown works only by accident

[reader.py:373-376](../aef_loader/reader.py#L373-L376): `__aexit__` clears `_stores` and sets
`_registry = None`. The README's own pattern
([README.md:66-72](../README.md#L66-L72)) uses the returned `tree` *after* the `async with`
block exits — which only works because each `ManifestStore` holds its own reference to the
registry object, keeping the registered buckets alive. Nothing documents or tests that
invariant, so a future refactor of the registry lifetime breaks every documented usage. Either
make `__aexit__` leave the registry alone, or document that the tree outlives the reader and
test it.

### A12 (P2) A year selection that matches nothing succeeds silently

[tessera.py:155](../aef_loader/tessera.py#L155):
`ds.sel(time=[t for t in sel if t in set(ds["time"].values.tolist())])`. Ask for 2030 and you get
a zone with a zero-length `time` dimension and no message. Warn, or raise naming the years the
store actually has.

### A13 (P2) `_candidate_zones` breaks across the antimeridian

[tessera.py:52-56](../aef_loader/tessera.py#L52-L56) assumes `west < east`; a bbox crossing 180°
produces an empty or inverted zone list.

## B. Usability

### B1 (P0) `query()` is `async` but awaits nothing — and the documented entrypoint breaks in Jupyter

**Verified**: [index.py:222-319](../aef_loader/index.py#L222-L319) contains **zero** `await`
expressions. It is pure pandas/shapely work declared `async`, which forces every caller into an
event loop for a synchronous filter.

The consequence lands in the README: [README.md:78](../README.md#L78) ends with
`asyncio.run(main())`, which **raises `RuntimeError: asyncio.run() cannot be called from a
running event loop`** inside a Jupyter notebook — the primary environment for this library's
audience. Nothing in the README mentions it.

Fix:
- make `query()` and `load()` plain `def` (keep `async` aliases if you care about compatibility);
- keep `download()` async, add a sync wrapper for scripts;
- add a README note: in a notebook, `await main()` directly instead of `asyncio.run(main())`.

### B2 (P0) Cold start downloads 78 MB of global index to answer one small bbox query

**Verified**: `Content-Length: 77829744` on the Source Coop index; `docs/PERFORMANCE.md` records
14.9 s for it. 302,466 rows covering the whole planet, to find the handful of tiles over an AOI.
See **C1** — 80% of those bytes are a geometry column the library never reads.

### B3 (P1) The default index cache directory is `/tmp`

[index.py:78](../aef_loader/index.py#L78): `self.cache_dir = cache_dir or Path("/tmp")`.
On Windows — the machine `docs/BENCHMARKS.md` says this was developed and benchmarked on — that
resolves to `C:\tmp`, a junk directory created at the drive root. On Linux it is wiped on reboot,
so the 78 MB download repeats. The README never mentions the cache exists or where it goes.
Use `platformdirs.user_cache_dir("aef-loader")` and document it.

### B4 (P1) `import aef_loader` pays for a geopandas import you may not need

[index.py:13](../aef_loader/index.py#L13) is a module-level `import geopandas`, and
[`__init__.py`](../aef_loader/__init__.py) imports `index` — so `from aef_loader import
open_tessera`, which needs no geopandas at all, still pulls in geopandas and pyogrio. Move it
inside `AEFIndex`.

### ~~B5 (P1) `rasterio` is a hard dependency and is never imported~~ — WITHDRAWN

~~Drop `rasterio>=1.4.4`.~~ **This was wrong.** No `rasterio` reference appears anywhere in
`aef_loader/`, but that is not the test that matters: `odc/geo/warp.py` does a module-level
`import rasterio.warp`, and `odc-geo` does not declare rasterio as its own dependency. **Verified**:
with odc-geo 0.5.3 installed and rasterio absent, `import odc.geo.warp` raises
`ModuleNotFoundError` — so `xr_reproject`, and therefore `reproject_datatree`, cannot even be
imported. [pyproject.toml:33](../pyproject.toml#L33) is correct as written. Credit to the Astra
review (§1.8) for catching this.

The underlying install-weight concern is still real, just differently shaped: GDAL comes in via
the reprojection path only. If that matters, the move is to make `odc-geo`/`rasterio` an optional
extra and have `reproject_datatree` raise a clear "install `aef-loader-plus[reproject]`" message —
not to drop the pin.

### B6 (P1) No `py.typed`

The package is fully annotated but ships no marker, so mypy and pyright treat it as untyped for
every downstream consumer. One empty file plus a hatch `include` entry.

### B7 (P2) Error messages don't say what was tried

`"No tiles provided"` ([reader.py:477](../aef_loader/reader.py#L477)), `"No datasets to
reproject"` ([utils.py:407](../aef_loader/utils.py#L407)), `"No TESSERA data found for the
requested bbox and zones"` ([tessera.py:171](../aef_loader/tessera.py#L171)) — none echo the
bbox, years or zones that produced the empty result, which is the whole question the user has at
that moment. [index.py:179](../aef_loader/index.py#L179) does this well; match it.

### B8 (P2) `__version__` is duplicated

Hardcoded `"0.1.0"` in [`__init__.py`](../aef_loader/__init__.py) and again in
[pyproject.toml:3](../pyproject.toml#L3). Use `importlib.metadata.version("aef-loader-plus")`.

### B9 (P2) CI is thinner than the project

[.github/workflows/tests.yml](../.github/workflows/tests.yml): one OS, one Python (3.12, though
`requires-python = ">=3.12"` claims 3.13 too), no ruff step despite `ruff` in `[dev]` and a
`.ruff_cache/` in the tree, no `[tool.ruff]` config at all, no lockfile — so a dependency release
can break `main` with no code change — and the `slow` live tests never run anywhere, not even on
a schedule. Add: a 3.12/3.13 matrix, `ruff check` + `ruff format --check`, and a weekly cron job
running `-m slow` so upstream drift in Source Coop or virtual-tiff surfaces before a user hits it.

## C. Speed and cloud-native

### C1 (P0) Project the index columns — the geometry column is 80% of the download and is never used

This is the largest single win available, and the honest version of it is not what a
cloud-native checklist would predict. I probed the live file:

| | |
|---|---|
| rows | 302,466 |
| **row groups** | **1** |
| page/offset index | **absent** |
| GeoParquet version | 1.0.0, WKB, **no bbox covering declared** |

Because the whole file is a single row group with no page index, **row-group and page-level
predicate pushdown are unavailable**. DuckDB + `httpfs`, pyarrow dataset filters, Overture-style
spatial pushdown — none of them can prune anything here. If a review tells you to reach for
DuckDB for this, it has not looked at the footer.

What *does* work is column projection, because each column chunk is its own contiguous byte
range. Per-column compressed sizes:

| column | compressed | % of file |
|---|---:|---:|
| `geom` (WKB) | 62.33 MB | **80.1%** |
| `location` | 5.64 MB | 7.3% |
| `path` | 5.51 MB | 7.1% |
| `fid` | 1.49 MB | 1.9% |
| all 15 others | 2.85 MB | 3.7% |
| **total** | **77.82 MB** | |

The columns `aef_loader` actually reads total **8.67 MB — 11.1% of the file**. Column projection
alone avoids **69 MB** per cold start, a ~9× reduction, and drops the geometry deserialisation
(302k shapely objects) along with it.

The catch, stated precisely: today's filter is
`gdf.sindex.query(bbox_geom, predicate="intersects")`
([index.py:266](../aef_loader/index.py#L266)), which needs `geom`. Without it you test overlap
against `wgs84_west/south/east/north` instead. AEF tiles are UTM-aligned squares, so their WGS84
footprints are slightly curved quadrilaterals and those four columns are the footprint's
*bounding box* — a superset. So a bbox-overlap test can return a few extra tiles at the margins
but **can never miss one**. Extra tiles are cheap when `bbox=` is passed to `open_tiles_by_zone`
(they crop to nothing — fix A10 first so they're skipped rather than kept as 0×0 arrays).

Recommended shape:

```python
# default: 8.67 MB, bbox-overlap prefilter on scalar columns
tiles = await index.query(bbox=bbox, years=(2020, 2023))

# opt in to the exact footprint test, pays the 62 MB for `geom`
tiles = await index.query(bbox=bbox, years=(2020, 2023), exact_geometry=True)
```

Note `geom_bbox` (a struct of xmin/xmax/ymin/ymax) already exists in the file and carries the
same information as `wgs84_*`, but is *not* declared as a GeoParquet 1.1 `covering`, so no
geo-aware reader will use it for pruning.

Effort: ~half a day. Expected: 14.9 s → ~2 s cold start, and B2 disappears.

### C2 (P0-adjacent, upstream) Ask for the index to be republished properly

The single row group and missing page index are upstream artefacts, not yours. A rewrite by
`tge-labs` with (a) many row groups sorted spatially (Hilbert or by `utm_zone`), (b) a
GeoParquet 1.1 `bbox` covering on `geom`, and (c) the page index enabled, would make genuine
predicate pushdown work and take the query to a few hundred KB. That is a small change on their
side and worth an issue — it benefits every consumer, not just this library. Until then, C1 is
the ceiling.

### C3 (P1) `max_concurrency` bounds metadata only — the pixel reads are unbounded

[reader.py:496-498](../aef_loader/reader.py#L496-L498) and
[reader.py:570-573](../aef_loader/reader.py#L570-L573): the semaphore wraps the header parse and
`open_zarr`. The actual chunk fetches happen later, inside dask, with no shared budget at all.
On a wall-to-wall AOI that is where essentially all the requests are, so the one knob the docs
tell users to tune (`docs/PERFORMANCE.md`: "values between 8 and 16") does not govern the phase
that dominates. Add a limit on the read path and expose it separately from the metadata limit.

### C4 (P1) Coalesce adjacent chunk range requests

The manifest holds exact byte ranges per COG block
([cache.py:399-407](../aef_loader/cache.py#L399-L407)). A windowed read across a contiguous block
row touches ranges that are adjacent or nearly adjacent in the file, and each currently becomes
its own GET. Merging ranges separated by less than some gap threshold — the standard trick, what
GDAL's `GDAL_MERGE_CONSECUTIVE_RANGES` does and what obstore's multi-range `get_ranges` exists
for — cuts request count several-fold on any AOI spanning blocks. **Check first** whether
VirtualiZarr's chunk-fetch path already reaches `get_ranges`; if it does, this is configuration
rather than code, and if it doesn't, it's an upstream feature request worth making.

### C5 (P1) Store the manifest cache as parquet/arrow, not JSON

[cache.py:402-408](../aef_loader/cache.py#L402-L408) writes `paths`/`offsets`/`lengths` as JSON
lists. For an 8192² tile that is 4,096 blocks × 64 bands ≈ 262k entries, with the full object
path repeated verbatim in every one. A parquet file with a dictionary-encoded path column, or a
plain `.npz`, would be one to two orders of magnitude smaller and skip `json.loads` +
`np.array` entirely.

Be clear-eyed about the size of this win: `docs/PERFORMANCE.md` already measures a disk cache hit
at 28 ms, so the latency gain is small. The real argument is disk footprint and I/O across a
wall-to-wall run. Combine it with a single combined manifest per `(zone, year)` so N small file
reads become one.

### C6 (P1) The proper fix for cold start: publish a virtual-Zarr or Icechunk sidecar

The manifest cache is a local approximation of something better: one pre-built virtual dataset
per zone/year, covering the whole AEF collection, so opening becomes a single metadata read with
no per-tile header parse at all. Icechunk or VirtualiZarr's parquet manifest format both do this,
and it subsumes C5 entirely. Larger effort, and it needs somewhere to host the sidecar — but it
is the 2026 answer to "why does opening 40 tiles cost 40 header parses", and it is the piece that
would let this library beat Earth Engine on wall-to-wall AOIs as decisively as it already beats
it on chips.

### C7 (P2) Keep obstore. Don't "modernise" to fsspec.

[reader.py:24](../aef_loader/reader.py#L24) already uses obstore, the Rust `object_store` binding.
That *is* current best practice for this workload; aiohttp/fsspec would be a step backwards.
Recorded here so it doesn't get changed by someone working from a generic checklist.

### C8 (P2) Zarr v3 sharding and GeoZarr — not applicable to reads

You do not control the source encoding; these are COGs in someone else's bucket. Sharding and
GeoZarr layout only become relevant if this project starts *writing* derived cubes (see D3).
GeoZarr is still a moving OGC spec — worth tracking for an output format, not for reads.

### C9 (P2) S3 Express One Zone, mountpoint-s3, S3 CRT — mostly hype here

Express One Zone requires the data in *your* single-AZ bucket, which means copying AEF; it only
pays off for a hot, repeatedly-scanned subset. mountpoint-s3 adds a POSIX layer this stack has no
use for. The CRT client's advantage is large sequential objects, not many small ranged reads,
where obstore's pooling is already the right shape.

The one co-location point that *does* matter and costs nothing: Source Coop is `us-west-2`
([constants.py:562](../aef_loader/constants.py#L562)). Running compute in that region beats every
item in this section combined, and deserves a line in the README.

### C10 (P2) Dask is the right choice here; a non-dask chip path is the exception

The graph is small and embarrassingly parallel, and `reproject_datatree`'s blockwise `xr.where`
([utils.py:438](../aef_loader/utils.py#L438)) already sidesteps the align-and-refragment trap
that `combine_first` would cause. Cubed would buy nothing. The one case where dask is pure
overhead is the single-chip read — which is exactly what `benchmarks/compare_chip_download.py`
measures and what D5 proposes promoting to the API.

### C11 (P2) GPU decode — no

int8 payload, lightly compressed COG blocks, network-bound. nvCOMP/DALI solve a problem this
workload does not have.

## D. Extensibility and future features

### D1 (P0) There is no dataset abstraction — AEF assumptions are welded into the reader

The concrete couplings:

| What | Where |
|---|---|
| `A00..A63` band naming applied to any band count | [reader.py:701](../aef_loader/reader.py#L701) |
| `set_aef_nodata` stamped unconditionally | [reader.py:704](../aef_loader/reader.py#L704) |
| `-128` as the join fill value | [reader.py:157-172](../aef_loader/reader.py#L157-L172) |
| AEF-specific quantization-curve error text | [utils.py:375-381](../aef_loader/utils.py#L375-L381) |
| `AEFTileInfo` as the only tile contract | [types.py:519](../aef_loader/types.py#L519) |
| `DataSource` as a two-value enum | [constants.py:548](../aef_loader/constants.py#L548) |

TESSERA was added by writing a parallel module that duplicates the zone loop, the bbox-to-pixel
maths and the CRS handling — and skipped the nodata stamping, which is precisely how bug **A2**
got in. A third dataset duplicates it a third time.

The seam: a `Collection` protocol carrying `{nodata, dtype, band_names, dequantize, zone_crs,
index_source}`, with `open_tiles_by_zone` and `reproject_datatree` reading their constants from it
rather than from module globals. **Do this before adding another dataset**, not after — the cost
only goes up, and A2 is the evidence.

### D2 (P1) No host abstraction

[reader.py:48-79](../aef_loader/reader.py#L48-L79) and
[index.py:130-150](../aef_loader/index.py#L130-L150) hardcode `gs`/`s3` parsing and per-host store
construction, with `skip_signature=True` baked in for Source Coop
([reader.py:396](../aef_loader/reader.py#L396)). Azure, a signed bucket, a local COG directory or
a plain HTTP host each mean touching both files. Seam: one `store_for(url, **options) ->
ObjectStore` factory with credentials passed by the caller.

### D3 (P0 for adoption) Zonal and point extraction

The most-asked-for thing for any embeddings library: *"give me the 64-dim vector at these N
points, or the mean vector over these polygons, as a DataFrame."* Right now every user writes it
themselves, and most will write it slowly — reprojecting an entire AOI mosaic to extract 200
points.

Hook point: a new `aef_loader/extract.py`:

```python
extract_points(gdf, years)   -> DataFrame  # one row per point, 64 embedding columns
extract_zonal(gdf, years, stat="mean") -> DataFrame
```

Group the geometries by UTM zone, convert to pixel indices per tile, and use vectorised fancy
indexing — no reprojection, no mosaic, no dask. Composes with C1: query the index for only the
tiles the points touch. High value, 1-2 days.

### D4 (P1) Chip and patch sampling for ML

`benchmarks/compare_chip_download.py` already demonstrates that chip extraction is this library's
competitive advantage over Earth Engine — but that capability lives in a benchmark script, not
in the API. Promote it: `read_chip(lon, lat, size, years)` and `chips(gdf, size)` returning numpy
arrays, plus a thin torch `Dataset` wrapper. This is the headline feature for the ML audience,
and per C10 it should bypass dask entirely.

### D5 (P1) A one-liner entrypoint and an xarray backend

Beyond fixing B1: the minimum viable snippet today is 12 lines and requires knowing three
classes. Add `open_aef(bbox, years, source=...) -> DataTree` that wraps download + query + open,
and register an xarray backend so `xr.open_dataset(..., engine="aef")` works. Discoverability is
most of adoption for a library like this.

### D6 (P1) Output formats

Nothing writes anything. In order of likely demand: (a) `to_zarr`/Icechunk for a persisted AOI
cube, (b) COG/GeoTIFF export of a reprojected slice, (c) parquet of per-geometry embeddings
(which D3 produces anyway). Hook point: a new `aef_loader/write.py` over the `reproject_datatree`
output. This is also where GeoZarr (C8) becomes a real question rather than a theoretical one.

### D7 (P2) CLI

`aef query --bbox`, `aef chip`, `aef warm-cache` — cheap with typer, genuinely useful for shell
and Make pipelines, and `warm-cache` in particular pairs well with the manifest cache.
Half a day.

### D8 (P2) STAC

A STAC collection/items view over the index would let people use `pystac-client` + `odc.stac` or
`stackstac` instead of this library's own API. Good for interop, but largely redundant with C1
once the parquet query is fast, and Source Coop does not currently publish one for AEF. Do it
only if being usable from existing STAC pipelines is a goal in itself.

### D9 (P2) Dataset registry via entry points

Once D1 exists, expose collections through
`[project.entry-points."aef_loader.datasets"]` so third parties can register their own embedding
collections without forking.

### D10 (P2) Upstream the bug fixes

`docs/CHANGES.md` states the fork's changes "were written so they can be proposed upstream". Two
are unambiguous bug fixes that would reduce the fork's divergence and help the upstream project:
the `chunks=None` materialisation fix (change A in `docs/CHANGES.md`) and **A3** above, which
upstream already has a `TODO` for. Worth opening as PRs while the diff is still small.
